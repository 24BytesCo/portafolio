Quien le vende al Estado colombiano conoce la rutina. Abrir el SECOP, escribir las mismas palabras de ayer, filtrar por departamento, revisar página por página y anotar en una hoja de cálculo lo que parece interesante. Todos los días, porque el proceso que sirve puede publicarse hoy y cerrar en una semana.

Construí [SECOP Monitor](https://secop.24bytes.pro) para quitar esa rutina de encima. Este artículo cuenta qué gana quien lo usa y, para quien le interese la parte técnica, cómo está hecho.

## El problema no es encontrar información, es enterarse a tiempo

La contratación pública colombiana es abierta. Los datos de SECOP I y SECOP II están publicados en datos.gov.co y cualquiera puede consultarlos. El problema es otro: son cientos de procesos nuevos cada día, repartidos entre miles de entidades, y nadie le avisa a un proveedor cuando aparece el suyo.

Las empresas grandes lo resuelven con una persona dedicada a revisar. Una constructora pequeña, un consultor independiente o una empresa de suministros no tiene a esa persona. Se entera tarde, o no se entera.

## Qué hace por quien lo usa

**Alertas que trabajan solas.** El usuario describe lo que vende con sus propias palabras, por ejemplo obra civil, placa huella, acueducto o interventoría. Elige departamentos, municipios, modalidades y un tope de valor. Desde ese momento el sistema revisa por él cada hora.

**Un resumen diario, no una avalancha.** Cada noche llega un correo, y un WhatsApp si el plan lo incluye, con los procesos nuevos que encajan, ordenados por relevancia. Cada proceso trae el objeto, la entidad, el valor y el enlace directo al SECOP.

**Seguimiento de los procesos que importan.** Cuando un proceso interesa, se marca para seguirlo. Si la entidad cambia los pliegos o mueve la fecha de cierre, el sistema lo detecta y avisa. Las fechas clave se pueden llevar al calendario del celular.

**Contexto para decidir si vale la pena presentarse.** Cada entidad, municipio y categoría tiene una ficha pública que muestra cuánto contrata, con qué modalidades y a qué ritmo. Antes de invertir días en una propuesta, se puede ver si esa alcaldía contrata sobre todo por mínima cuantía o si casi todo lo adjudica de forma directa.

**Guías para quien está empezando.** El [registro en SECOP II](https://secop.24bytes.pro/guias/registro-en-secop-ii), el RUP, los requisitos habilitantes y los errores que hacen rechazar una oferta, explicados sin jerga, con cursos gratuitos y certificado verificable.

Se puede empezar gratis con una alerta, sin tarjeta.

## Cómo está construido

### Ingesta: datos abiertos, cada hora

Un proceso programado consulta la API de datos abiertos (Socrata) de SECOP I y SECOP II cada hora y guarda lo nuevo en PostgreSQL. Solo se reprocesa un registro cuando sus metadatos cambiaron, de modo que la ingesta es barata aunque la base tenga cientos de miles de procesos.

Como todo depende de una fuente externa, hay una sonda que cada cinco minutos comprueba si el SECOP responde y publica el resultado en una [página de estado](https://secop.24bytes.pro/estado-secop). Cuando el portal oficial se cae, los usuarios lo saben sin tener que adivinarlo.

### El matcher: búsqueda de texto completo en PostgreSQL

No hay un motor de búsqueda aparte. Cada proceso tiene un vector de búsqueda en español, sin tildes, y las palabras clave de cada alerta se convierten en una consulta de texto completo. La relevancia sale de la propia base de datos:

```sql
SELECT id, ts_rank("searchVector", q) AS score
FROM "Proceso", websearch_to_tsquery('spanish', unaccent('obra civil OR acueducto')) q
WHERE "searchVector" @@ q
  AND departamento = 'MAGDALENA'
  AND "createdAt" >= now() - interval '1 day';
```

A ese puntaje se le suman reglas propias de la alerta, como modalidad, municipio y rango de valor. Mantenerlo todo en PostgreSQL significa una sola pieza que respaldar, monitorear y pagar.

### Una lección reciente: los campos de texto libre callan las alertas

Hace poco un usuario creó una alerta y no recibió nada. Tenía la demanda, porque había decenas de procesos que le servían, pero en el campo de departamentos había escrito el nombre de un municipio junto al del departamento. El matcher comparaba por igualdad exacta y esa alerta no podía coincidir con nada. No había error, no había aviso, solo silencio.

El arreglo tuvo tres capas. El asistente ahora solo acepta departamentos de un catálogo y, si alguien escribe un municipio con su departamento, los separa solo. La API rechaza lo que no reconoce con un mensaje claro. Y el matcher compara sin distinguir mayúsculas ni tildes. La lección vale para cualquier producto: un filtro que puede dejar un resultado vacío sin explicación es un error esperando a ocurrir.

### Frontend que Google puede leer

La aplicación es Angular con renderizado en servidor. Las fichas públicas y las guías llegan al navegador como HTML completo, así que cargan rápido en un celular y los buscadores las leen sin ejecutar JavaScript. La parte privada, que es el tablero de cada usuario, se renderiza solo en el cliente.

### Notificaciones y cobro

El correo sale por Resend y el WhatsApp por la API oficial de Meta, con plantillas aprobadas. El cobro va por ePayco, con un webhook firmado e idempotente para que un pago confirmado dos veces no active dos veces nada.

### Operación: nada expuesto, nada directo a producción

Todo corre en contenedores detrás de un túnel de Cloudflare y un proxy que solo escucha en localhost. Ningún contenedor publica un puerto a internet. Cada cambio pasa primero por un entorno de QA que se despliega solo, y llega a producción únicamente después de probarse ahí. Las migraciones de base de datos en producción se revisan a mano antes de aplicarse.
